Field guide · single-source shortest paths · C-HD (Vals AI, Sept 2026)

Reading the bound with your hands

O( n + m + m·log(2 + m⁄(n+1)) + m⅓·(n·log(n+2))⅔ )

TL;DR. This is the runtime bound for C-HD, a directed shortest-path algorithm that ten Claude Opus 5.5 agents designed and proved in Lean (Vals AI writeup). n is vertices, m is edges. The bound is linear time, plus a penalty that grows with density, plus a cube-root blend of m and n log n. It only holds in a certified range, m ≤ n·⌊⌊log₂n⌋¾⌋; outside that, C-HD hands off to Bellman–Ford. The exponent race, 1959 → C-HD

Every bound here fits one picture. Give the graph an average degree of d = logα n, so α = 0 is road-network sparse and α = 1 is where m reaches n log n. Divide each running time by n and what's left is log n raised to some power. That exponent is the y-axis. Lower is faster, and the flat line at 1 is the sorting barrier: the n log n cost of emitting vertices in sorted order. It held for 40 years.

In action: why "sorting barrier"?

Dijkstra finalizes vertices one at a time, in exact distance order, so as a side effect it sorts all n vertices by distance. That sorting is where the n log n comes from. C-HD, like the Duan et al. algorithms before it, gets under that by not insisting on the order: run bounded local searches out from the frontier, charge newly touched vertices against a size limit, and only keep a heap over a thinned-out set of "pivot" vertices that organize the recursion. The right panel shows the band idea (Δ-stepping), which is a simpler cousin of the real algorithm, on the same graph.

07

Inside C-HD, step by step

Section 06 showed the general trick: don't insist on sorting. Here is how C-HD does it. Each call takes a frontier, runs one bounded local search per frontier vertex, and stops a search once it has discovered k vertices. Vertices it touches but can't improve still count toward that size limit, as unexplored leaves. Searches that hit the limit become trees whose roots are kept as pivots; searches that run dry finish their small patch on the spot. Only pivots go into the priority structure, and the recursion tree does the rest in bounded batches.

Fine print

Where the bound comes from. C-HD, from a Vals AI writeup (Sept 20, 2026): ten Claude Opus 5.5 agents coordinating on a message board designed it in about 15 hours and proved correctness and the runtime bound in Lean (proof repo). Directed graphs, non-negative real weights, exact distances. The bound holds for m ≤ n·⌊⌊log₂n⌋¾⌋; outside that the program runs Bellman–Ford. It's a blog post with a machine-checked proof, not yet a peer-reviewed paper.

The +2 and +1. Pure guards. log(2 + …) never drops below 1, and n + 1 never divides by zero. They change nothing asymptotically.

Reference formulas used. Dijkstra binary heap (n+m)log n; Fibonacci heap m + n log n; d-ary heap with d = m/n, 2m·log n / log d; Duan, Mao, Mao, Shu, Yin 2025, m·log⅔n; Duan, Mao, Shu, Yin 2026, m√log n + √(mn·log n·log log n); Bellman–Ford nm; BFS n + m. All logs base 2, all constants 1.

Why constants = 1 matters. Big-O hides constants and the new algorithms have large ones (recursion, pivot finding, block data structures). The crossings in sections 02 and 05 show where the formulas cross, which is a statement about growth, not stopwatch time.

Model assumptions. Directed graph, real non-negative weights, only comparisons and additions on weights. With integer weights on a word RAM, other algorithms (Thorup's linear-time undirected result, for one) change the picture.

Street data. Road snapshots from OpenStreetMap, fetched via the Overpass API in Sept 2026 and contracted to intersections: drivable and pedestrian highway types, one-way tags and roundabouts honored, clipped to a small box, and trimmed to the largest strongly connected piece so every intersection is reachable from any start. © OpenStreetMap contributors, ODbL.
